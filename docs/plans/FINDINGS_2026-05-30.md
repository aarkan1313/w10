## CODE BUGS (fix these — they affect runtime behavior)

### B1 [HIGH] — Wg10PagePool leaks GPU RIDs in the review scene and the M5 detail gate

**What's true.** `Wg10PagePool` is `#[class(base=RefCounted)]`
([page_pool.rs:43](../../wg-10/rust/src/page_pool.rs#L43)). It allocates page textures + a cached compute
context on the global `RenderingDevice`. The *only* code that frees those GPU RIDs is `free_all()`
([page_pool.rs:445](../../wg-10/rust/src/page_pool.rs#L445)), and its own docstring says the GDScript
owner must call it before the pool goes out of scope
([page_pool.rs:441](../../wg-10/rust/src/page_pool.rs#L441)).

**Why it leaks.** There is **no `Drop` impl, no `_notification`/PREDELETE, no `_exit_tree`** anywhere in
`page_pool.rs` (verified by grep). A Godot `Rid` is a POD handle — dropping the Rust struct does **not**
free the underlying GPU resource. So when the `RefCounted` pool's last reference drops, the page textures
and compute context are orphaned on the device.

**Where it bites.**
- [m3_review.gd:58](../../wg-10/worldgen_terrain/harness/m3_review.gd#L58) creates + configures a pool and
  has **no** `free_all`/`_exit_tree`/`_notification` (grep returned nothing). Every review-scene launch
  leaks a pool's worth of page textures + compute RIDs.
- [m5_detail_check.gd:65-67](../../wg-10/worldgen_terrain/m5/m5_detail_check.gd#L65) carries a comment that
  is **factually wrong**: *"Wg10PagePool is RefCounted — it releases its pages/RIDs automatically when the
  last reference drops."* It does not (no Drop impl). The same wrong belief is repeated at
  [m5_detail_check.gd:196](../../wg-10/worldgen_terrain/m5/m5_detail_check.gd#L196). This gate runs every
  `--suite m3`, so it leaks per gate run.

**Why it matters.** Repeated scene launches / gate runs accumulate orphaned page textures + cached compute
RIDs, which can skew perf gates (resource pressure) and eventually exhaust the rendering device.

**The one place that does it right:** the hardened perf gate calls `pool.call("free_all")`
([m5_perf_hardened_check.gd:193](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L193)) — so
this is a *missing-teardown* bug at two specific sites, not "nobody frees."

**Fix (pick the structural option, then patch the call sites):**
1. **Structural (preferred):** give `Wg10PagePool` a `Drop` impl that calls the existing `free_all()`
   logic, so the RIDs are released whenever the pool is dropped regardless of caller discipline. (Guard
   for "no RenderingDevice" exactly as `free_all` already does at
   [page_pool.rs:447](../../wg-10/rust/src/page_pool.rs#L447).) This makes leak-freedom structural and
   removes the footgun the wrong comments grew around.
2. **Belt-and-suspenders:** still add explicit teardown at the GDScript owners — an `_exit_tree()` (for the
   Node-hosted review scene) / end-of-function `free_all()` call in m3_review.gd, and replace the wrong
   comment in m5_detail_check.gd (lines 65-67 and 196) with an explicit `pool.call("free_all")` before
   return (mirroring what m5_perf_hardened_check.gd already does).
3. Delete/replace the "RefCounted frees RIDs automatically" comments — they are actively misleading and
   are the root of why the two sites omit cleanup.

### B2 [HIGH] — Coarsest "hold last-good" can display stale/wrong terrain after pool eviction

**What's true.** On a render-path miss for the coarsest level, `terrain_view` keeps the tile visible by
doing nothing — "HOLD LAST-GOOD" ([terrain_view.rs:128](../../wg-10/rust/src/terrain_view.rs#L128)),
implemented as a bare `continue` at
[terrain_view.rs:139](../../wg-10/rust/src/terrain_view.rs#L139). The tile stays bound to its current
`Texture2Drd` wrapper *and* its current transform/page uniforms.

**Why it can go wrong.**
- A released page stays **resident and LRU-eligible** — `release()` only unprotects
  ([page_policy.rs:131](../../wg-10/rust/src/page_policy.rs#L131)).
- Eviction **reuses the same texture RID and recomputes a different page's content into it in place** —
  `AllocateEvicting` does no `free_rid`/`texture_create`; it recomputes into the existing RID
  ([page_pool.rs:291-306](../../wg-10/rust/src/page_pool.rs#L291)) and the wrapper "still points at the
  same RID; content was recomputed in place"
  ([page_pool.rs:327-330](../../wg-10/rust/src/page_pool.rs#L327)).

**The failure mode.** A coarsest tile left on HOLD-LAST-GOOD is bound to RID *X* with page-A's
transform/origin/span uniforms. If page-A is released → becomes LRU-eligible → slot *X* is evicted and
recomputed for page-B, the tile now samples **page-B's pixels through page-A's geometry/uniforms** =
terrain that is geometrically placed for A but textured with B. Nothing in the bind path re-validates that
the held RID still maps to the held page's key before displaying it.

**Honest scope (from Review B, verified).** At default capacity the coarsest 3×3 stays protected/resident,
so this doesn't trigger in normal flying — the gates pass. The point is that the **never-black guarantee
holds by capacity headroom, not by construction.** Under capacity pressure (smaller pool, more levels,
denser eviction) the guarantee is not structural. This is consistent with the project's own never-black
work, which was tuned for `lead > coarse-span` + `budget >= coarse-column` at default capacity — it was
never proven to survive eviction of a held coarse page.

**Fix (make never-black structural, not capacity-dependent):**
- In the HOLD-LAST-GOOD branch, re-validate before holding: confirm the tile's currently-bound RID still
  corresponds to the page key it was last set for (e.g. the pool exposes "is slot *S* still mapped to key
  *K*?" / the view records the key it bound and checks `get_resident_page(key)` returns the *same* RID).
  If the held page is no longer resident-as-itself, the tile must not keep displaying it.
- **Protect held coarsest pages from eviction** while a tile is actively displaying them (extend the
  existing `protected` set in `page_policy` to cover "currently-bound last-good" pages), so the reuse path
  at [page_pool.rs:291](../../wg-10/rust/src/page_pool.rs#L291) can never recycle a slot out from under a
  visible tile. This is the structural fix and matches the existing protection mechanism.
- Add a gate that runs under **deliberate capacity pressure** (pool small enough to force coarse eviction
  during motion) and asserts no held tile ever shows content from a different page — a property the
  current default-capacity gates can't catch.

## GATE TRUST (fix these — a green number is currently weaker than it reads)

### B3 [MEDIUM] — Hardened perf gate's "did-real-work" proof can pass without proving terrain/detail

This directly tensions with the project's own rule ("bake did-real-work asserts INTO the perf gate or the
number is worthless"). The gate *tries* to honor it, but the proof is satisfiable without real terrain.

**What's true.**
- The frame background is bright sky `Color(0.45, 0.62, 0.85)`
  ([m5_perf_hardened_check.gd:91](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L91)).
- The nonblack test counts a pixel as "real" if `c.r > 0.03 or c.g > 0.03 or c.b > 0.03`
  ([m5_perf_hardened_check.gd:159](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L159)), with
  floor `MIN_NONBLACK := 0.85`
  ([m5_perf_hardened_check.gd:49](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L49)).
  → A **100%-empty-sky frame scores `nonblack = 1.000` and passes** the nonblack assertion. The proof
  cannot distinguish terrain from sky.
- Detail is set once to `DETAIL_AMP`
  ([m5_perf_hardened_check.gd:70](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L70)) and
  **never compared on-vs-off** in this gate, so a fly-scale detail regression (detail silently
  contributing nothing) still passes. (The on/off diff exists only in the separate
  `m5_detail_check.gd`, and only at one static page.)

**What works (don't over-correct).** `MIN_PRIMITIVES := 100000`
([m5_perf_hardened_check.gd:51](../../wg-10/worldgen_terrain/tests/m5_perf_hardened_check.gd#L51)) does
catch a fully-empty-geometry frame, and the GPU-time measurement is genuinely real (real
`viewport_get_measured_render_time_gpu`, not wall time). The gap is specifically the *nonblack* and
*detail* proofs.

**Fix:**
- Make nonblack a **terrain-vs-sky** test, not "any bright pixel." Either sample only the lower frame
  against the known sky color (count a pixel real only if it differs from `(0.45,0.62,0.85)` by a
  threshold), or render against a black/zero background for the nonblack-sampling pass so sky can't satisfy
  it.
- Add a **detail-on vs detail-off** assertion to this gate (capture one reference frame at
  `wg_detail_amp = 0` and assert the moving render differs by more than a floor), so a detail regression
  fails the *perf* gate too — not only the separate static-page detail gate.

### A-C1 [CLOSED — recorded as a negative result, not an open item]

Review A's headline technical finding: the offline "spectral-fidelity" gate proved the *signature carries a
spectrum* via a circular iFFT path (`synthesize_field`, which round-trips by construction and tiles), while
the actual runtime basis (`synthesize_value_noise_fbm`) was never tested and caps at cos ≈ 0.83 — i.e. the
gate did not exercise the path it claimed to prove (verified at `tools/dem_pack/spectral.py` +
`test_spectral.py`). **This is now resolved by the owner having abandoned spectral synthesis entirely**
(structure = phase, which a power-spectrum discards). Kept here only so the lesson isn't relearned: a
round-trip gate that writes amplitudes into the same bands it reads proves nothing about the shipping
basis. The replacement direction is the north-star "local NMS-style functions" vision, not spectral.
